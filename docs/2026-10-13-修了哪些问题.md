# limo-app 修了哪些问题

> 2026-10-13 的改动记录。
>
> 只讲四件事：发现了什么、为什么它是问题、改成了什么样、怎么确认改对了。

## 起因是一条红的测试

本来只是想跑一遍测试，看看改动之前是什么状态，好有个基线。

```
Tests run: 3, Failures: 0, Errors: 1
NoSuchMethod 'java.util.Map PythonCoreClient.convert(String, String, String)'
```

测试 mock 的是三个参数的 `convert`，而实现早就改成五个参数了。Mockito 是运行期匹配，编译期看不出来，所以这条测试在签名改掉的那天就坏了，之后一直没人发现——也就是说，这套代码对外宣称的三条保证——账务准确性、配额两层、并发防超扣——
实际上一条都没有测试兜着，而且其中一条连跑都跑不起来。

顺着这条线往下读代码，又翻出九个问题。下面按「会不会真出错」排。

---

## 一、会真出错的四处

### 1. 「失败不扣」当时是句空话

`TaskService.process()` 里的顺序是这样的：先调核心拿到消耗，然后 `deductPoints` 扣积分，再落笔记。落笔记这一步如果抛异常，会被外面的 `catch` 接住——接住之后只做了一件事：把任务状态标成 FAILED。

积分不会退。

发现它的过程很普通：读那段代码的时候，注意到 `deductPoints` 和 `noteRepo.save` 中间隔着四行，于是顺手 grep 了一下 `@Transactional`，全项目只出现在 `UserRepository` 的三个 `@Modifying` 上，Service 层一个都没有。也就是说扣积分和落笔记根本不在一个事务里。

改法是把「扣积分 + 落笔记 + 改任务状态」三步包进一个 `TransactionTemplate`。这样任何一步抛异常，整个事务回滚，积分回到原样。

验证方式单独写了一条集成测试 `TaskSettlementTest`：把 `NoteRepository` 换成 mock、故意让 `save` 抛异常，然后断言积分没变。为了确认这条测试真的在测东西，我把断言值改成 `before - 3` 又跑了一次，它红在 `expected: 7 but was: 10`——说明实际值确实是原样。

### 2. 任务状态是读-改-写，两个线程能同时认领

```java
t.setStatus("PROCESSING");
taskRepo.save(t);
```

先查出来、改字段、再存回去。两个线程同时跑到这里，都能读到 PENDING，都能写成功，于是同一个来源被处理两遍、扣两次积分。

让我确定这是 Bug 而不是有意为之的，是对比：同一个项目里，扣用户积分用的是条件更新——

```sql
update User u set u.points = u.points - :cost where u.id = :id and u.points >= :cost
```

判断和写入在同一条 SQL 里交给数据库。任务认领凭什么就能读改写？同一个仓库里两种写法，必然有一种是错的。

改成 `compareAndSetStatus(id, from, to)`，由数据库保证只有 PENDING 能变成 PROCESSING，返回 0 就说明已经被别人认领了。测试里开了八个线程同时抢同一个任务，只有一个能成功。

### 3. 版本号靠内存算，并发下会撞车

同一来源重新生成会产生新版本，原先版本号是这么算的：把该来源所有笔记查出来，取第一条的版本加一。

并发下两个请求会算出同一个号。而且我去翻了 `Note` 实体，`(userId, sourceId, version)` 上没有任何唯一约束，撞了也没人拦。

改成由数据库聚合：`select max(version) from note where ...`，同时在实体上补了唯一约束当最后一道防线。测试里两条都验了——正常递增，以及故意插一条重复版本号，确认数据库真的会拒绝。

### 4. 套餐查不到时返回 null，后面直接 NPE

```java
return planRepo.findByCode(u.getPlanCode())
        .orElseGet(() -> planRepo.findByCode("free").orElse(null));
```

返回 null 之后，调用方下一行就是 `plan.getNoteLimit()`。如果配置表里连 free 都没有（比如初始化脚本没跑），用户看到的会是一个空指针，堆栈指向 `.getNoteLimit()`，跟真正的原因（套餐缺失）隔着十万八千里。

改成 `.orElseThrow(...)` 并写清楚缺的是哪个套餐。少一种失败方式，比多一段兜底逻辑划算。

## 二、读代码的人容易顺手翻的三处

### 5. 四种失败挤在一个 FAILED 里

积分不够、核心连不上、文件读不了、我们自己写错了——全都落成 `FAILED`，前端只能显示「失败」，用户不知道该充值、该重试、还是该换个文件。

这个问题我在 LiMo-C 里已经解决过一次：那边原本所有降级都标 `truncated`，后来按「用户能采取的行动」重新划成了 8 态，还把判据写进了 `patterns.md` 第 53 条。同一个洞察，在这个项目里没有落地。

改法是新增 `failReason` 字段，分四种：`NO_POINTS`（去充值）、`CORE_DOWN`（稍后重试）、`BAD_INPUT`（换个文件）、`UNKNOWN`（联系我们）。分类由 `TaskStatus.reasonOf()` 按异常码做，单独写了单元测试。

有一条规则我特意收窄了：只有明确的 502 才算 `CORE_DOWN`，其余的 5xx 一律归 `UNKNOWN`。因为把「配置缺失」说成「核心不可用，请重试」，用户重试一百次也不会好——归错类比不归类更糟。

### 6. 全项目只有一个类有日志

grep 一下 `@Slf4j`，只有 `DevController` 上有。主流程里的 `catch (Exception e)` 把异常吞掉、只改个状态就完事，任务失败了你自己都不知道为什么。

现在 `TaskService` 加了 `@Slf4j`，失败时按原因分级：能归类的 `warn`，归不了类的 `error` 并带上堆栈——因为没分类的失败就是 bug，不留堆栈等于下次还得再查一遍。

### 7. 测试只有三个，其中一个还是坏的

这一条就是开头的起因。改完从 3 个变成 14 个，新增的三类分别针对：结算事务、并发认领、失败原因分类。

## 三、收拾一下就能好的三处

### 8. 两个处理方法几乎一模一样

`process()` 和 `processFile()` 各七十来行，只有两处不同：调的是 `process` 还是 `processFile`，以及最后要不要删临时文件。配额校验那三行也在 `createTask` 和 `createTaskFromFile` 里各写了一遍。

现在提交路径收敛成一个 `submit()`，执行路径收敛成一个 `run()`，两个版本的差别只剩传进去的一个 lambda。以后给其中一个加逻辑，不会漏掉另一个。

### 9. 配置文件里躺着明文密码

```properties
spring.datasource.password=88888888
jwt.secret=limo-secret-key-please-change-me-in-production-0123456789
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
```

第一行是本地密码，第二行更麻烦：JWT 的签名密钥一旦泄露，任何人都能自己签发一张合法的登录凭证。

有意思的是 python-core 那边反而做对了——`config.yaml` 里的 `api_key` 留空、靠环境变量注入。同一套系统两侧，一侧做对一侧没做。

现在全部改成 `${ENV:默认值}` 的形式，本地照样能起来，生产必须注入。并且把 `show-sql` 默认关掉。

### 10. 状态是字符串，列表不分页

状态原先到处是 `"PENDING"` 这种字面量，拼错一个字母编译器不管。收进了 `common/TaskStatus`。

笔记列表原先一次性把该用户所有笔记查出来返回，笔记越多接口越慢。现在由数据库分页，`size` 夹在 1 到 500 之间，不传参数时返回最近 200 条。

## 怎么确认没改坏

跑 `./mvnw test`，14 个测试全绿。其中 `LimoFlowIntegrationTest` 是改动前就有的全链路测试（注册 → 订阅 → 提任务 → 扣积分 → 落笔记 → DONE），它通过说明原有链路没被动过。

另外对最关键的「失败不扣」做了一次负向对照：把断言值故意改错，确认它真的会红。测试通过只说明测试跑了，不代表它测到了东西。
