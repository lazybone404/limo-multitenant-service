# limo-app 设计文档

> 记录这套「跨语言后端」的关键设计决策、为什么这么设计、边界在哪。
> 面向：后来动这块代码的人。

## 0. 一句话

**Java 管"商业"（用户/订阅/积分/配额），python 管"能力"（内容→笔记）。Java 只记账、让核心自报消耗，对外卖能力不露底。**

---

## 1. 为什么跨语言（Java + Python）

- **Java**：多租户、订阅计费、并发、鉴权，是求职主方向，且 Java 生态做企业级业务最稳。
- **Python**：AI 处理（文档/视频提取、LLM 生成）生态最成熟；核心能力在 C 端已验证可用。
- **差异化**：不是"只写一个 CRUD"，而是"一个真实可用能力 + 完整商业化闭环"。这是简历最大亮点。

### 诚实边界
- Java 端是**完整、可跑、可测**的；python-core 的**生成层当前是 mock**（`USE_MOCK=True`，未配真实 LLM key），但**底层能力本人已用/已验证**。简历说"Java 业务端 + 跨语言整合"，不要吹"我写了 AI 核心的完整实现"。

---

## 2. 对外契约：卖能力，不露底

- **对用户**：只看到"文档/视频 → 笔记"这个能力 + 套餐价，**看不到**用哪个模型、内部算法、成本。
- **落点**：`python /convert` 返回的 note 是纯笔记（mock 已去掉"占位返回/未配置 key"字样）；Java 响应不带模型信息。
- **token/积分是对内计量**：用户看到的是套餐 + 白话额度（"月付 19.9 约转 X 篇/ Y 小时"），不是"1积分=1000token"。
  - 白话额度由核心 `estimate` 折算（预留 `POST /estimate`），Java 侧持有 token→积分 换算率（1积分=1000token，可配置）。

---

## 3. 核心自报消耗（关键设计）

**问题**：计费按什么算？文档/视频/多模态的消耗各不相同，Java 硬编码"字符/4、分钟×1000"会在多模态失效，且暴露内部算法。

**方案**：**核心自报 `usage`**。
- `python /convert` 返回 `{note, raw_text, duration, usage:{tokens, cost}}`
- **Java 不自己算 token**（`TokenCalculator` 只做 token→积分 换算），只看核心报的 `tokens`
- 好处：
  1. 核心是黑盒，消耗逻辑归属核心（单一职责）
  2. 多模态（图片/音频/混合）平滑扩展——Java 只认 `usage.tokens`，完全不用改
  3. 对外不暴露"我按什么模型成本估算"

**落地**：`TaskProcessorImpl` 读 `usage.tokens` → `TokenCalculator.costPoints(tokens)` → 记账。

## 4. 计费机制（机制级，不追生产级）

**按用户要求：不做预扣，任务处理完再算账。**

```
提交：校验配额 → 建任务 PENDING → 异步
处理：调核心 → 拿 usage.tokens → 折算积分 → 条件扣积分
      成功 → 落 note + 任务 DONE
      失败 → 不扣费，任务 FAILED
```

- **条件更新防超扣/负积分**：`update User set points=points-:c where id=:id and points>=:c`，返回 0=余额不足
- **失败不扣**：catch 里不扣积分（用户任务挂了不能白扣钱）
- **不做预扣/现金流/完美幂等**：明确是机制级，够演示、够讲、够验证，不吹生产级

### 为什么留"条件更新"而不是分布式锁
- 单条扣费用**数据库条件更新**已经原子、够用（并发安全）
- 分布式锁（Redisson）在 library-service 做过、能讲，但这里单纯扣积分用条件更新更简单——**讲出来高并发无超卖要靠条件更新/悲观锁，我能讲清**

## 5. 数据模型：来源 ↔ 产物（对齐 C 端）

C 端（LiMo-C）用 `store.py`（文件+JSON 索引），模型是 `transcript(来源) ↔ markdown view(产物，可多版本)`。

**Java 端继承模型、不继承存储**：
- 继承：**来源/产物分离 + 可多版本**
- 存储：**MySQL 规范化**（多租户要 `userId` 隔离、并发、备份、扩展——文件存储对多租户 SaaS 不合适）

| 表 | 职责 | 关键字段 |
|---|---|---|
| `app_user` | 账号+积分+套餐 | points, planCode, status |
| `src` | 来源（url/文件/文本）| userId, sourceType, origin |
| `note` | 笔记资产 | userId, sourceId, version, content(TEXT), title, preview, tokens, points |
| `task` | 一次转换+计费 | userId, sourceId, status, tokens, points |
| `plan` | 套餐 | price, grants, noteLimit |

### 为什么内容存 MySQL TEXT 而不是对象存储
- 笔记是纯文本 Markdown、量小，MySQL TEXT 简单可靠、好 join。
- **进阶口（只讲不做）**：量大了/含图片/要全文检索 → 挪 OSS/S3 + ES。写进文档当扩展路径。

## 6. 配额（免费/付费不同）

**双维度配额**：
| 配额 | 管什么 | 按什么算 |
|---|---|---|
| `noteLimit` | 用户**存**多少篇笔记 | 篇数 |
| `points` | 用户**生成**多少次 | token 消耗 |

- `plan.noteLimit`：free 30 / monthly 500 / yearly 3000（`PlanSeeder` 初始化）
- **校验时机**：提交任务时 `count(note) >= noteLimit` → 409 拒绝（**在扣积分前拦截**，避免扣了又不让存）
- **删除释放**：删笔记后 count 下降，自动回到配额内

---

## 7. 并发 / 多用户 / 异步 / 幂等 / 隔离

| 点 | 实现 | 留口（只讲不做） |
|---|---|---|
| 扣积分 | 数据库条件更新（原子，防超扣） | 分布式锁（Redisson 做过能讲） |
| 慢任务 | 线程池 `taskExecutor` 后台处理 | MQ 削峰（`TaskProcessor` 接口已抽象） |
| 幂等 | 同用户同来源处理中 → 不重复创建 | |
| 数据隔离 | task/note 都校验 `userId` | |
| 外部依赖 | python 调用超时/重试/降级（不拖垮主流程） | |

### 留口子说明（重要：别把「设计上可扩展」说成「已经做了」）
- **`TaskProcessor` 是接口**，现在是「调 python」，将来可加 MQ 实现。**但 MQ 没有真做**：
  设计上可扩展，当前靠数据库状态机 + 线程池保证，没有引入 Kafka / RabbitMQ。

---

## 8. 幂等 / 任务状态机

- `PENDING → PROCESSING → DONE / FAILED`
- 失败时另有 `failReason` 说明原因（`NO_POINTS` / `CORE_DOWN` / `BAD_INPUT` / `UNKNOWN`），
  按「用户能采取的行动」划分，不按异常类型划分（2026-10-13 加）
- 幂等去重：同用户、同来源、还在 `PENDING/PROCESSING` → 复用已有任务，不重复扣费/重复调 python。**注意**：这里幂等只在"处理中"去重，任务失败不自动重试（机制级不展开）。

---

## 9. 鉴权

- JWT（JJWT 0.12）签发/校验；`JwtInterceptor` 拦截 `/api/**`（`/api/auth/**` 放行）
- BCrypt 存密码（`spring-security-crypto`，不动整套 security）
- `UserContext` ThreadLocal 存当前 userId，`UserContext.get()` 取
